# DAVYLAB 公众号选题工作台｜应用与工程规则

本文件用于 ChatGPT、WorkBuddy 及后续开发者执行同一套规则。遇到冲突时，优先遵循用户最近明确指示、当前线上产品实际行为，以及数据/安全边界；不可把旧计划当作已实现功能。

## 1. 仓库与工作范围
- 主仓库：`chenzhe223-tech/chenzhe223-tech.github.io`
- 工作分支：`main`
- 工作台路径：`topic-studio/`
- 线上入口：https://chenzhe223-tech.github.io/topic-studio/
- Davy Radar：https://chenzhe223-tech.github.io/radar/daily/
- 当前每日素材数据：https://chenzhe223-tech.github.io/radar/data/latest.json
- 对工作台的修改应直接落在该仓库现有代码上；修改前先读取最新文件，避免在其他仓库重复建站。

## 2. 产品定位与用户体验
- 产品目的：帮助 DAVYLAB 从 AI 新闻/开源项目、个人开发实践与灵感中发现、判断、管理和推进公众号选题。
- 品牌主张：把想法，做成能用的工具。
- 内容风格亲近、真实、简洁；不写成冰冷的产品说明书，不为了“爆款”夸大事实。
- 选题评分是辅助决策，不是阅读量或爆款预测。
- 选题页面应清晰、对齐、对称、高级、易用。参考 Dribbble、Land-book 的设计品质，但不照搬单一页面。
- 色彩克制：深海军蓝/蓝灰做品牌识别，浅灰白画布、白色卡片，少量科技蓝用于主操作和选中状态。避免大量高饱和色、装饰堆叠和过密小字。
- 保留现有功能。UI 改造不能删掉自然语言选题入口、念头盒导入、选题池、排期、提示词、已发内容等已有能力。

## 3. 新闻/选题素材配图规则
1. 每张素材卡片都应有图片区域，不再使用单调纯色方块作为正式新闻缩略图。
2. 优先读取 Davy Radar 结构化数据提供的真实图片字段 `image_url`；如有 `image_fallback_url`，按数据约定使用。
3. GitHub Skill 条目可使用对应 GitHub 仓库的社交预览图；必须链接到相应项目页面。
4. 没有新闻原图时，按标题/摘要关键词匹配主题辅助图片；fallback 必须明确标注为“主题配图”或同义说明，不能冒充新闻原始照片。
5. 图片加载失败时依次使用备用图；最终失败应明确显示图片不可用状态，不能让空白或破损图片造成错误印象。
6. 图片应等比例裁切（`object-fit: cover`），不拉伸，不遮挡文章标题；桌面端使用三列布局（图像、正文、操作），手机端图文并列、操作区放下方。
7. 图片有明确 alt 文本，并展示可访问的来源链接/来源说明。来源字段不能臆造；当只是主题图片时必须和新闻来源区分。
8. 不抓取或展示与新闻无关的图片，也不把生成图片描述成真实截图。使用外部图时遵守原站可用性、来源标注和相应许可；不能保证永久可用，应有 fallback。
9. QA 至少验证：每张可见素材卡片有图片元素，HTTPS URL、alt、fallback 字段存在；桌面三列正确排序；手机图片可见、操作区完整、页面无横向溢出；失败图片可降级。

## 4. 选题内容质量
- 保留原始素材标题、出处和链接；AI 生成的选题角度只是建议，用户需根据 DAVYLAB 的读者和品牌重新判断。
- 优先考虑读者价值、时效性、实操性、差异化、品牌契合度五项；打分不能当作流量预测。
- 新闻素材应先阅读原文和核对日期；不得只根据摘要扩写确定性结论。
- 不虚构指标、采访、用户反馈、产品功能、使用效果或来源。未核实内容标注“待确认”。
- 对自有产品需区分概念、开发中、已实现、已验证/上线状态。截图、架构图或演示数据不自动证明生产能力已验证。
- 给 ChatGPT 的创作提示词应包括：目标读者、差异化角度、可核查来源、结构/形式建议、真实素材清单、事实核查清单；允许模型建议放弃不值得写的选题。

## 5. 公众号已发内容库
- 共享档案文件：`topic-studio/data/published-articles.json`。
- 目前工作台读取共享 JSON，并可在本地浏览器保存手动新增的文章。**本地记录不会自动提交 GitHub，也不会自动跨设备同步。**
- 同步记录必须来自 DAVYLAB 公众号后台真实“已发表/发表记录”或可验证的永久文章链接。草稿、预览链接、编辑链接不得冒充已发表内容。
- 首次/每次同步时按文章永久 URL 去重，保留旧记录；不得因为某页/某次分页没显示而删除已有历史数据。
- 必填字段至少包括正式标题、永久 URL；发布日期尽可能填入。栏目、摘要、封面缺失时留空，不能猜。
- 导入文件需验证 JSON schema；同步后重新打开线上工作台刷新共享档案，核对条数、标题、发布日期、链接及最后同步时间。
- 当前已记录 3 篇公众号发布内容，最后同步时间为 `2026-10-23T12:20:00+08:00`；详情以共享 JSON 当前内容为准。

## 6. 微信官方 API 与凭证安全
- 不能仅凭有 AppID 就假定已开放“获取已发表内容”接口；先在公众号后台核对当前账号主体、认证状态和接口权限。
- 未确认权限前，不宣称已经与微信公众号 API 自动关联。
- 如后续开发 API，同步逻辑必须运行在 Cloudflare Worker 或其他服务端；AppSecret、access_token、Cookie、密码和验证码不得出现在前端 HTML、公开 JSON、GitHub 提交、日志或聊天输出里。
- 不得绕过登录、扫码、验证码或平台权限；遇到安全验证交由账号所有者本人完成。
- 当前可用的替代流程是：WorkBuddy 经授权浏览器从后台核验已发表记录，更新 GitHub 共享 JSON，并报告同步数量、去重数、缺失字段和同步时间。

## 7. WorkBuddy 执行纪律
- 先核验仓库、分支和目录，再操作；目标仓库是 `chenzhe223-tech/chenzhe223-tech.github.io`、分支 `main`。
- 若 WorkBuddy 报告找不到 `topic-studio/` 或同步指南，应先切换至正确仓库/工作目录，不要立即新建重复全套项目。
- 修改已有文件前读取最新版、采用小范围改动，并检查与未合并变更的冲突。
- 完成后重新读取变更文件/运行测试，保留 commit、Actions、文件路径等可验证证据。
- 用户要求同步历史或规则时，应保存可检索文档，并从 README 提供入口。
- 不声称后台操作、图片加载或接口调用成功，除非工具/日志/实际页面有证据。

## 8. 内容发布安全边界
- ChatGPT 负责选题、研究、稿件、版式和核查；WorkBuddy 经授权在公众号后台录入并保存草稿；正式发布由用户本人最终确认。
- “稿件已准备”“草稿已保存”“手机预览通过”“正式发表”是不同状态，不可混用。
- 贴图与图文文章使用各自对应的编辑规则，不能把完整网页预览 HTML 当作公众号正文。
- 标题、封面、正文分离；主标题只在标题字段出现一次，正文不重复封面或标题海报。
- 正文图片必须实际上传到公众号编辑器，不能依赖本地 file URL。
- 公众号封面规格采用用户确认的要求：头条封面 1800×766 px、约 2.35:1、JPG/PNG、≤2 MB；若编辑器需要 1:1 分享卡，则另做方图。
- 正式发布前必须重新生成手机预览并检查首屏、字体、行距、对比度、图片顺序/比例、尾段是否完整。旧临时预览链接不能作为最终验收证据。
- 用户提供的真实公众号二维码必须使用原图；禁止生成式模型伪造二维码。

## 9. 数据存储与同步
- 当前选题记录主要保存在 `localStorage`；不同浏览器/设备的本地数据互不自动同步。
- 公众号已发内容的共享列表由 GitHub 上的 JSON 供给；由 WorkBuddy/人工同步后其他设备可读取最新共享档案。
- JSON 导入/导出是迁移本地选题和文章记录的备用方式。
- 未来要做跨设备选题同步，需要明确账号身份、访问控制、并发冲突、备份与隐私设计，再选择 Cloudflare Worker、D1/R2 或其他后端；不能把共享公开 JSON 当作私有数据库。

## 10. 变更与验收最低标准
每次提交前至少确认：
- [ ] 对应功能不是静态摆设，关键按钮有实际行为。
- [ ] 不删除当前既有功能。
- [ ] 无语法错误、控制台/pageerror 或关键请求失败。
- [ ] 桌面端与常见手机端布局正常，无横向溢出。
- [ ] 涉及图片时检查来源、加载失败降级、alt 和裁切。
- [ ] 涉及文章数据时测试导入/导出、去重、空值和链接验证。
- [ ] 涉及共享档案时确认 JSON schema 与前端渲染兼容。
- [ ] README / 操作指南与实际实现一致。
- [ ] Actions 成功后再报告“部署/验收通过”；如果只通过部分测试，明确剩余项。
